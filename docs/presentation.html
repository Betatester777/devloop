What is DevLoop?

A structured workflow where AI agents collaborate to build software

📄

Document-Driven

Every decision, requirement, and design lives in a document. Nothing is implicit. Documents are the single source of truth that all agents follow.

🚦

Phase-Gated

Work progresses through defined phases. Each transition requires a quality gate to pass — no skipping steps, no cutting corners.

🔗

Fully Traceable

Every requirement gets a unique ID that flows through plans, code, tests, and releases. You can trace any feature from idea to delivery.

📦

Small Increments

Work is broken into feature bundles — each independently testable and deliverable. One bundle at a time, fully completed before the next.

🤖 The Agents

Seven specialized AI agents, one orchestrator to lead them

Agent Roster

Each agent has a single responsibility and produces a specific deliverable

🤖 Orchestrator Coordinates the workflow — reads state, selects phases, invokes agents, enforces gates docs/STATE.md
📋 Product Manager Turns your request into structured requirements with testable acceptance criteria docs/PRD.md
🏗️ Software Architect Designs modules, interfaces, and technical decisions from the requirements docs/ARC.md
📐 Task Planner Breaks the architecture into 3–8 concrete, implementable tasks per bundle docs/PLN.md
💻 Developer Implements exactly the planned tasks — code, unit tests, nothing more src/ + tests/
🧪 Tester Verifies the software against requirements — tests come from the PRD, not from code docs/TST.md
🔍 Review Presenter Assembles a review package with demo steps so you can try the software before approving docs/REV.md
📦 Release Manager Creates user-facing release notes, packages the deliverable as a versioned zip releases/

How Agents Work Together

The orchestrator is the single point of control — agents never talk to each other directly

🤖

Orchestrator Controls Everything

Reads the current state, decides which phase comes next, invokes the right agent, validates the output, and updates the state. No agent acts without being called.

👤

You Talk to the Orchestrator

All user-facing prompts (accept/improve, approval, version numbers) come from the orchestrator — never from sub-agents. One conversation, one point of contact.

📝

Documents Are the Interface

Each agent reads input documents and writes output documents. The PRD flows into the architecture, the plan flows into the code, the tests flow into the review.

🔒

Document Ownership

Each document has exactly one owning agent. Only the owner can modify it. This prevents conflicts and ensures accountability for every artifact.

🛠️ Skills

Seven reusable procedures that agents follow to produce consistent results

Skills

Standardized procedures ensure every agent produces high-quality, consistent output

💾

State Management

Reads and writes workflow state. Tracks current phase, active bundle, repeat count, and blockers. Can infer state from existing documents if interrupted.

📋

PRD Authoring

Structures raw user input into feature bundles with REQ-N IDs and testable acceptance criteria with AC-N.M IDs using Given/When/Then format.

🏗️

Architecture Design

Decomposes requirements into modules, interfaces, and technical decisions. Identifies risks and ensures every feature bundle maps to at least one module.

📐

Bundle Planning

Breaks a feature bundle into 3–8 tasks with dependencies, definitions of ready/done, validation commands, and AC traceability.

🧪

Requirements Testing

Designs tests from requirements, not source code. Every acceptance criterion gets at least one test. Expected behavior always comes from the PRD.

🔍

Review Packaging

Assembles a self-contained review package: change summary, test results, risks, runnable demo steps, and clear approval questions.

📦

Release Notes

Generates user-oriented release notes with what's new, migration steps, known issues, and a traceability table linking requirements to commits.

🔄 The Workflow

From idea to tested, released software in defined phases

Workflow Phases

Every project follows the same path — requirements first, then design, then build-test-review cycles

🚀 Init Capture request
→
📋 Requirements Write the PRD
→
🏗️ Architecture Design modules
→
🔁 Increment Cycle Plan → Build → Test
→
🔍 Review User approves
→
📦 Release Package & ship

The Increment Cycle repeats for each feature bundle

Work is split into feature bundles (3–8 tasks each). The cycle runs once per bundle: plan the tasks, implement them, test against requirements. If tests fail, the developer fixes and retests — up to 3 attempts before escalating.

What Happens in Each Phase

Every phase has a clear input, a responsible agent, and a defined output

  • 🚀 Init — The orchestrator captures your project name, summary, requirements, and tech stack. Writes the user request and auto-transitions to Requirements.
  • 📋 Requirements — The product manager creates a PRD with feature bundles (REQ-1, REQ-2…) and testable acceptance criteria (AC-1.1, AC-1.2…). You review and accept.
  • 🏗️ Architecture — The architect designs modules, interfaces, and technical decisions based on the PRD. You review and accept.
  • 📐 Planning — The task planner picks the next feature bundle and breaks it into 3–8 concrete tasks with dependencies and validation commands.
  • 💻 Implementation — The developer implements each task in order: writes code in src/, writes tests in tests/, runs pytest + ruff after each task.
  • 🧪 Testing — The tester independently verifies the software against requirements. Tests come from the PRD, not from reading the code. Pass gate is automated.
  • 🔍 Review — The review presenter assembles a review package with demo steps. You choose: Approve & Release, Approve & Next Bundle, or Needs Rework.
  • 📦 Release — The release manager creates user-facing release notes and packages a versioned zip archive in releases/.

🚦 Quality Gates

Every phase transition must pass its gate — no exceptions

Quality Gates

Four gates ensure nothing ships until it's ready

✅ Ready

Bundle has scope, acceptance criteria, dependencies, and validation commands defined

✅ Pass

All tests pass, lint is clean, validation commands exit with code 0

✅ Accept

User reviews the increment and explicitly approves it

✅ Release

Release notes, traceability table, and versioned zip archive are complete

Documents Produced

  • PRD.md — Requirements with REQ/AC IDs
  • ARC.md — Architecture and design
  • PLN.md — Task plan with traceability
  • TST.md — Test results and evidence
  • REV.md — Review package with demo steps
  • REL.md — Release notes for users

Traceability Chain

  • REQ-1 → Feature bundle in the PRD
  • AC-1.1 → Testable acceptance criterion
  • Tasks → Each traces back to AC IDs
  • Tests → Each verifies specific AC IDs
  • Commits → Reference REQ/AC in messages
  • Release → Maps REQ → AC → commits

YOLO Mode ⚡

Fully automated — no user approval needed, releases after every cycle

Normal Mode

  • You review and accept the PRD
  • You review and accept the architecture
  • You choose which bundle to work on
  • You approve or reject at review
  • You decide whether to release
  • You choose the version number

YOLO Mode

  • PRD is auto-accepted
  • Architecture is auto-accepted
  • Next pending bundle is auto-selected
  • Review auto-approves
  • Release runs after every cycle
  • Version auto-increments (minor)

Quality gates are always enforced

YOLO mode skips human approval — not automated checks. Tests must still pass, lint must be clean, and all acceptance criteria must be verified. The workflow just doesn't stop to ask you.

Getting Started

Three commands to know

▶️

/devloop-start

Start a new workflow from scratch. The orchestrator will ask for your project name, summary, requirements, and tech stack.

⚡

/devloop-bulk-yolo-start

Provide a structured request and let it run fully automated. No approvals needed — just watch it build, test, and release.

⏩

/devloop-continue

Resume a workflow from where it left off. The orchestrator reads the saved state and picks up at the right phase.

📊

/devloop-status

See current phase, active bundle, progress, and what happens next. Read-only — no workflow actions taken.

📝

/devloop-bulk-start

Like bulk-yolo but with approval steps. Provide structured input, and the workflow asks you to confirm at each phase.

🧹

/devloop-cleanup

Clean up transient artifacts or perform a full reset. Source assets and releases are always preserved.
