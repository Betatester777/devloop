The Problem

Why governance matters in agentic software engineering

⚡

Generation is fast, but review is hard

AI agents can produce code, tests, and documentation quickly. Without orchestration, output quality is inconsistent and reviewing every change becomes a bottleneck.

🔀

Intent and implementation can drift

When design decisions, requirements, and code are not explicitly linked, teams lose traceability. Changes happen in isolation, and verification becomes unreliable.

❌

Unconstrained autonomy is risky

Without evidence-based gates, incorrect code or untested changes can propagate downstream. Scope, quality, and release discipline erode.

👁️

Accountability gets lost

Who decided what? Why was that code generated? Is that test valid? Without persistent artifacts and clear ownership, these questions become impossible to answer.

Operating Model

DevLoop separates governance, execution, and evidence into distinct roles

👤

Human as Governor

Sets project intent, reviews high-impact tradeoffs, approves release decisions. Moves from hands-on coding to supervisory control at meaningful checkpoints.

🤖

Orchestrator as Control Layer

The only component allowed to advance the workflow. Manages state, routes work, enforces gates, escalates ambiguity. Single point of control keeps the system predictable and auditable.

🔧

Specialists Execute Bounded Tasks

Each agent owns one phase and produces one artifact. Agents do not negotiate with each other; they work through orchestrated context and return control immediately.

📦

Durable Artifacts Carry Intent

Requirements, plans, tests, and release evidence persist and remain versioned. Artifacts are the contract between phases, not ephemeral prompts.

System Roles

Each role has a single responsibility and produces a specific output

🤖 Orchestrator Owns control flow, state, routing, policy, retries, and gate enforcement. The only active manager of phase transitions. STATE.md
📋 Requirements Engineer Transforms user intent into testable requirements and acceptance criteria with explicit scope and success measures. PRD.md
🏗️ Architect Designs modules, interfaces, and key technical decisions. Bridges requirements to implementable structure. ARC.md
📐 Task Planner Breaks the architecture into 3–8 concrete, interdependent tasks with validation commands and acceptance criterion traceability. PLN.md
💻 Developer Implements planned tasks: writes code, adds unit tests, runs checks. Stops at boundaries; does not redesign or skip validation. src/ + tests/
🧪 Tester Independently verifies behavior against requirements. Tests come from PRD intent, not from reading code. TST.md
🔍 Review Presenter Assembles a self-contained review package: change summary, test evidence, risks, demo steps, and explicit approval questions. REV.md
📦 Release Manager Creates user-oriented release notes, traceability table, and versioned deliverable package. REL.md + zip

Governance & Control Flow

Three layers: human decision, orchestration, and specialist execution

Lifecycle Phases

Eight phases from goal capture to release, each with explicit ownership and exit criteria

  • 1. Capture Intent — Define the goal, constraints, initial scope, and success measures.
  • 2. Specify Requirements — Turn intent into testable requirements and acceptance criteria with explicit scope.
  • 3. Design Solution — Choose structure, interfaces, and key technical decisions. Bridge requirements to implementation.
  • 4. Plan Increment — Break the next bundle into 3–8 concrete tasks with dependencies and validation commands.
  • 5. Implement — Produce code, unit tests, and local validation evidence. Stop at boundaries.
  • 6. Verify Requirements — Test from intended behavior, not from implementation assumptions. Trace back to PRD.
  • 7. Review with Evidence — Present change summary, test results, risks, and demo steps for approval.
  • 8. Release Increment — Package the approved result with release notes and traceability table.

Rework and retry loops

If verification fails, the orchestrator returns to implementation with the failure report. Up to 3 attempts before escalating to review. This keeps the system efficient while preventing infinite loops.

Traceability Model

Bidirectional links connect requirements forward into design, code, and release evidence

➡️

Forward Traceability

Each requirement flows into design decisions, planned tasks, implemented code, test cases, and release documentation. Coverage checks confirm that no requirement is orphaned.

⬅️

Backward Traceability

Every delivered artifact traces back to a justified requirement. Code, tests, and documentation exist because a requirement demanded them, not by accident.

🔍

Trace Enforcement

Automated checks block incomplete work from advancing. If a test has no parent requirement, it is flagged. If a requirement has no test, the release gate fails.

📊

Traceability Report

Release package includes a full traceability matrix: REQ-N → AC-N.M → Task → Code files → Test cases → Release notes. Everything is auditable.

Evidence Gates

Phases advance only when required artifacts exist and gate criteria pass

Ready Gate

Scope, acceptance criteria, dependencies, and validation commands are defined and reviewed.

Verified Gate

Tests pass, lint is clean, validation commands succeed, and trace links are complete.

Approved Gate

Human or policy explicitly approves the increment based on evidence and traceability.

Shipped Gate

Release notes, traceability table, and versioned package are complete and archived.

Gates are not optional

The workflow does not advance on confidence or agent self-reporting. It advances when the required artifact exists and the corresponding checks pass. This is what makes evidence-based delivery reliable.

Modes of Operation

Guided mode for evolving scope; supervisory mode for stable, policy-driven workflows

Guided Mode

  • Human approves the PRD
  • Human approves the architecture
  • Human selects which bundle to implement
  • Human reviews evidence before release
  • Human approves the version number
  • Best for: evolving scope, complex tradeoffs, learning phases

Supervisory Mode (YOLO)

  • PRD auto-accepted if scope is clear
  • Architecture auto-accepted per policy
  • Bundles auto-selected and executed
  • Evidence must still pass all gates
  • Version auto-increments; human monitors
  • Best for: stable policy, reliable constraints

Supervisory mode does not remove discipline

Tests still run. Traces still validate. Gates still enforce. The difference is that human approval is replaced with policy-based automation, but the engineering rigor remains absolute.

Getting Started

Six commands to operate DevLoop

🚀

/devloop-start

Launch a new workflow in guided mode. The orchestrator will ask for project name, goal, requirements, tech stack, and validate your input.

⏩

/devloop-continue

Resume from saved state. The orchestrator reads STATE.md, infers the current phase, and continues the workflow at the right place.

📊

/devloop-status

Read-only inspection. Shows current phase, active bundle, progress, completion percentage, and what happens next. No workflow changes.

🧹

/devloop-cleanup

Remove transient artifacts or reset the workflow. Source assets and releases are always preserved. Useful when retrying from a checkpoint.
